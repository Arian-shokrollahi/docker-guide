# multi-stage-->in docker file
---
## اول بریم سراغه اینکه چرا ما از multi stage استفاده میکنیم

ا-Multi-stage Build در Docker روشی است که با استفاده از آن می‌توان یک Dockerfile را به چند مرحله یا Stage تقسیم کرد. هر Stage می‌تواند وظیفه مشخصی داشته باشد؛ برای مثال یک Stage برای نصب وابستگی‌ها و Build کردن برنامه و Stage بعدی برای اجرای نسخه نهایی برنامه.

## هدفه ما از اینکه میایم اون dockerfile رو به مالتی استیج تبدیل میکنیم چیست:
هدف اصلی Multi-stage این است که ابزارها، فایل‌ها و وابستگی‌هایی که فقط در زمان Build لازم هستند وارد Image نهایی نشوند. در نتیجه Image نهایی سبک‌تر، تمیزتر و مناسب‌تر برای محیط Production خواهد بود.

### به این هم توجه کنید 
در Multi-stage هر دستور `FROM` یک Stage جدید ایجاد می‌کند و با استفاده از `AS` می‌توان برای آن Stage نام تعیین کرد. سپس در Stageهای بعدی می‌توان با دستور `COPY --from=` فقط فایل‌ها یا خروجی‌های موردنیاز را از Stage قبلی دریافت کرد.

---
### حالا بریم سراغه اینکه ما چرا از مالتی استیج در داکر فایل استفاده میکنیم
دلایل اصلی استفاده از **Multi-stage Build** این‌هاست:

- کم کردن حجم `Image` نهایی
- حذف ابزارهای Build مثل compiler و package manager از Image نهایی
- جلوگیری از ماندن فایل‌های اضافی و موقت داخل Image
- جدا کردن محیط **Build** از محیط **Runtime**
- بهتر شدن امنیت Image نهایی
- مناسب‌تر شدن Image برای محیط `Production`
- ساده‌تر شدن نگهداری Dockerfile
- امکان استفاده از چند محیط مختلف در یک Dockerfile
- کپی کردن فقط خروجی نهایی موردنیاز با `COPY --from`
- کاهش زمان `pull` و `deploy` به‌خاطر کوچک‌تر شدن Image

---
## دلیل اهمیتش در محیط production

در محیط **Production** اهمیت Multi-stage بیشتر میشه، چون Image نهایی باید تا حد ممکن **سبک، امن و فقط شامل فایل‌های ضروری برای اجرای برنامه** باشه. ابزارهای Build، سورس‌های اضافی و dependencyهایی که فقط هنگام ساخت برنامه لازم بودن، در Production معمولاً کاربردی ندارن و فقط حجم و سطح حمله رو بیشتر می‌کنن.

دلایل اهمیتش در Production:

- ا-`Image` کوچک‌تر → `pull` و `deploy` سریع‌تر
- ابزارهای اضافی کمتر → امنیت بیشتر
- ا-dependencyهای غیرضروری کمتر → آسیب‌پذیری کمتر
- محیط Runtime تمیزتر و قابل‌کنترل‌تر
- مصرف Storage کمتر روی سرور
- انتقال Image بین Registry و Server سریع‌تر
- نگهداری و عیب‌یابی ساده‌تر
- مناسب‌تر برای CI/CD و Deployهای مکرر
